# Project Recon

Use this reference when the target stack is unclear, the project contains competing patterns, or a new framework or dependency is being considered.

Recon is read-only until you know what the page should extend.

## Goal

Learn enough to make the next page fit the project. Do not inventory the whole repository when the target route and nearby files already answer the question.

## Fast Recon Workflow

### 1. Find the Target

Identify:

- The route or URL.
- The template, view, or page component.
- The shared layout or application shell.
- One or two nearby pages that represent current practice.

If the user named a file, begin there.

### 2. Identify the Runtime and Rendering Method

Read the relevant manifests and project files. Determine:

- Framework and language.
- Template or component syntax.
- Server rendering, static generation, client rendering, or a mixed approach.
- Package manager and build commands.

Do not rely on one marker when the project contains several applications. Follow the target route to the code that renders it.

### 3. Identify the Styling System

Check the target and nearby pages for:

- Native CSS, CSS modules, Sass, or CSS-in-JS.
- Utility or component frameworks.
- Theme variables, design tokens, spacing scales, and breakpoints.
- Existing dark mode and responsive conventions.

Native CSS is an existing styling system. Keep it by default. Do not ask whether to replace it unless the user requested a wider styling change.

### 4. Find Reusable UI

Look for existing:

- Page shells and layout components.
- Headers, navigation, forms, buttons, cards, tables, and feedback states.
- Icon components, icon libraries, and approved SVG assets.
- Metadata helpers and structured-data generators.
- Image components and asset pipelines.
- Motion utilities.

Reuse a current pattern when it meets the need. Do not copy a deprecated or isolated example without checking nearby usage.

If no icon system exists, do not fall back to emoji, raster icons, or hand-written inline SVG. Use a clear text label when the icon is optional. When the interface genuinely needs a consistent icon set, choose an established library that fits the stack and dependency policy. SVG generated by that library is allowed, as are existing SVG assets provided by the project or user.

### 5. Check Content and Assets

Locate the content source and available facts:

- Static content, CMS fields, database data, or route parameters.
- Existing logos, product images, portraits, illustrations, and Open Graph images.
- Known names, dates, links, prices, contact details, and legal text.

Record what is known and what is missing. Do not fill missing facts with realistic-looking guesses.

### 6. Choose the Implementation Path

Use this order:

1. Existing project pattern or tool.
2. Simple native HTML, CSS, or browser behavior.
3. A small local implementation consistent with the codebase.
4. A new dependency only when it solves a real gap and fits the project.

A user request for a specific framework or library can change this order, but still check compatibility and scope.

### 7. Ask Only When Needed

Ask one short question when an unknown choice changes:

- Which application or renderer owns the route.
- Whether a new system should replace an existing one.
- A paid service, license, or external data source.
- Public content, privacy, or business facts.
- A major dependency or page structure.

Do not ask about choices that nearby code or the user's brief already settles.

## Recon Summary

Report findings only when they help the user understand a decision. Keep it short:

```text
Target: account settings route in the existing server-rendered app
UI: current native CSS and shared form components
Assets: existing brand mark, no page image needed
Decision: reuse the current shell and add no dependency
```

For a simple edit, recon can remain internal.

## Anti-Patterns

### 1. Guessing the Stack From Habit

* **The Bad Habit:** Generating the framework or syntax the agent uses most often without tracing the target route.
* **The Problem:** The page does not compile, render, or match nearby code.
* **Why It Fails:** The user must replace the implementation instead of reviewing the intended page change.
* **Clean Fix:** Start at the route or named file, then inspect its shell, imports, manifests, and neighboring pages.
* **The Waitsec Way:** Read the path that renders the page before choosing syntax.

### 2. Treating Native CSS as Missing Infrastructure

* **The Bad Habit:** Seeing plain CSS and proposing a utility framework before attempting the requested page with existing styles.
* **The Problem:** A page task turns into a styling migration and build configuration change.
* **Why It Fails:** The diff grows, established styles compete, and the page becomes harder to maintain.
* **Clean Fix:** Keep native CSS and reuse its variables and patterns. Discuss a framework only when the user asks for a broader change or the existing setup cannot meet the need.
* **The Waitsec Way:** Existing simple tools are valid tools.

### 3. Adding a Parallel UI System

* **The Bad Habit:** Mixing a new utility or component framework into a project that already has a working system.
* **The Problem:** Resets, tokens, component behavior, and spacing rules disagree.
* **Why It Fails:** The page looks inconsistent and future edits require knowledge of both systems.
* **Clean Fix:** Extend the current system. If replacement is intentional, treat it as a separate migration with clear scope.
* **The Waitsec Way:** One coherent system is easier to use and change.

## Recon Checklist

- [ ] Did I trace the actual target route or template?
- [ ] Did I inspect nearby current pages instead of relying only on manifests?
- [ ] Did I identify rendering, styling, tokens, reusable UI, and existing generators?
- [ ] Did I check real content and project assets before inventing or sourcing anything?
- [ ] Does the chosen path reuse project tools or a simple native solution?
- [ ] If a dependency is proposed, is the gap and cost clear?
- [ ] Did I avoid asking questions the project already answered?

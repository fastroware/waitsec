# About, Profile, and Portfolio Blueprint

Use this guide for a personal profile, founder page, team member page, developer portfolio, or professional biography.

Apply [`waitsec-ui`](../../waitsec-ui/SKILL.md) for layout, components, accessibility, and copy. Use [`seo-and-structured-data.md`](./seo-and-structured-data.md) only when the page is public and indexable. When a portfolio or profile needs a real visual identity rather than the project's existing system, choose a direction from [`visual-styles.md`](./visual-styles.md) or run [`design-direction.md`](./design-direction.md) before styling.

## Choose the Page Type

First identify what the page is for:

- A short personal introduction.
- A professional biography.
- A portfolio for clients or hiring teams.
- A founder or team profile.
- A public identity page connected to published work.

The type decides what evidence and contact options belong. Do not force a portfolio layout onto a short biography.

## Factual Content

Use known information only:

- Name and current role.
- Short description of work or focus.
- Real projects, case studies, writing, or experience.
- Dates and organizations that can be published.
- Approved portrait, avatar, or brand image.
- Public profiles and contact methods.
- Availability only when current and confirmed.

Do not invent employers, impact numbers, client names, testimonials, availability, or profile links.

## Section Menu

| Section | Use when |
| :--- | :--- |
| Introduction | The page needs identity and current focus. |
| Selected work | Public work or approved case studies support the page goal. |
| Experience | A work history helps the intended audience. |
| Skills or tools | Categories add useful context beyond the projects. |
| Writing or talks | Real publications or events exist. |
| Contact | A public contact path is approved. |
| Social profiles | The profiles are active, relevant, and intended for sharing. |

A portrait, timeline, skill list, availability badge, and direct email are all optional.

## Showing Work

Prefer a small set of meaningful examples over a long grid. A work item can use:

- A public live link.
- A public repository.
- An approved screenshot.
- A case study describing the problem, role, constraints, and result.
- A private-work summary that does not expose protected details.
- A publication, package, talk, or reference that demonstrates the work.

Do not require a public repository for proprietary work. State limits honestly.

## Contact and Privacy

- Use only contact methods the person approved for public display.
- A contact route can be safer than printing an email address.
- Do not expose a home address, personal phone number, or precise location by default.
- If availability is shown, make sure the content owner can keep it current.
- External profile links need clear labels and safe project conventions.

## Responsive Behavior

- Keep the introduction short enough to reach the main proof without excessive scrolling.
- Let project layouts become a readable single flow on narrow screens.
- Keep timelines left aligned or use a simple list when a split layout becomes cramped.
- Avoid dense clouds of skill badges.
- Keep external actions large enough to use without making every item a large button.

## Anti-Patterns

### 1. Fake Skill Ratings

* **The Bad Habit:** Assigning percentages, star ratings, or animated bars to human skills without a defined measurement.
* **The Problem:** The page presents precise-looking numbers that have no stable meaning.
* **Why It Fails:** Readers cannot compare or verify the ratings, so the display weakens confidence in the real work.
* **Clean Fix:** Group relevant skills plainly or connect each skill to a project, role, or result where it was used.
* **The Waitsec Way:** Show evidence of ability instead of invented precision.

### 2. A Timeline Forced Into Every Profile

* **The Bad Habit:** Building a long visual career timeline even when the page needs only a short biography or a few current roles.
* **The Problem:** Dates and decoration take over the page while the useful identity and work become harder to find.
* **Why It Fails:** The structure follows a portfolio template instead of the audience's question.
* **Clean Fix:** Use a short role list, selected milestones, or no history section when that better fits the page goal.
* **The Waitsec Way:** Page structure follows the story that exists.

### 3. Work Cards With No Useful Proof

* **The Bad Habit:** Listing many generic project names with vague claims and no explanation of the person's role or result.
* **The Problem:** Every item looks interchangeable and cannot support the claims being made.
* **Why It Fails:** Readers cannot tell what was built, what the person contributed, or why the work matters.
* **Clean Fix:** Show fewer items with a factual problem, contribution, constraint, result, and available proof. Respect private-work limits.
* **The Waitsec Way:** A clear case study is stronger than a large placeholder grid.

## Page Checklist

- [ ] Does the structure match the real page type and audience?
- [ ] Are identity, role, dates, organizations, results, and availability factual?
- [ ] Does selected work show a useful contribution and an allowed form of proof?
- [ ] Are portrait, timeline, skills, contact, and social links included only when useful and approved?
- [ ] Does the mobile flow keep identity and main proof easy to reach?
- [ ] Are private work and personal contact details protected?
- [ ] If indexable, does metadata describe the same person and visible content without duplication?
